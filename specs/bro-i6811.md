# bro-i6811 — proactive rate-limit cooldown in bro's serve conductor

## Problem

On 2026-11-10 `bro serve :8787` answered a client's requests by spawning
**147 devin-acp sessions**. The account answered `429`/`529`, the conductor
reported the wall — and the client's next request spawned **again**. The
account-wide rate limit (reset 20:01 UTC) was the symptom; the respawn was
the cause.

### The evidence (`<git-common>/bro/serve-turns.jsonl`, 1336 events)

| event | count |
| --- | --- |
| `acp.spawn` | 147 |
| `conductor.deadloop` | 32 |
| `conductor.error` → 529 | 60 |
| `conductor.error` → 429 | 51 |

The journal repeats one cycle, hour after hour:

```
acp.spawn → 529 "dv-acp unavailable — Internal error" → next request
          → 429 "acp dead loop: scope …"     → next request
          → acp.spawn → 200
```

The 429s split in two: **32** are bro's own dead-loop refusal (spec
`bro-b961a`) and **19** are the account's own wall —
`"devin-acp unavailable — Reached free model rate limit"`. The 60 529s are
the provider failing to serve (`"Internal error"`, `"Internal error: Invalid
op"`).

### Why the existing guard could not cover it

The dead-loop guard (`spec bro-b961a`) is *reactive* and it lives on the
**peer**:

- `pool.onDeath(() => guard.forgetPeer(...))` resets the peer tally when the
  peer dies — and a wall is exactly what kills the peer, so the churn
  measure restarts from zero on every wall;
- the guard counts **sessions opened and not completed**, which only reaches
  its budget after the churn has already happened;
- the refusal lands **after** the session was already paid for: the spawn
  happened, the session was opened, and only then did the guard notice.

The lane-cooldown is the **proactive** half: the account's own "no" closes
the spawn path, so the refusal costs no session and no quota.

### Why the knob that looked like it would help is dead

`~/.config/bro/config.json` carries `providers.devin-acp.rateGate`
(`{lane, requestsPerHour, spawnCost, burst}`) — but `laneGateAdmission`
only answers for **batch** spawns. The interactive serve path never asks it,
so the knob is inert exactly where the incident happened (bead `bro-56o2a`).

## Design

One module, `packages/providers/src/acp-cooldown.ts`, one lane-scoped
accounting, one config key. Like the guard, the cooldown is *accounting*,
not a heuristic: it counts the walls bro already knows about.

### G5 — the wall cooldown (the spawn path closes)

The cooldown lives on the **lane**, not on a conversation and not on a peer:

- a lane is the provider behind a route; every conversation on it shares
  the same account, so a wall that hit one conversation closes the lane for
  all of them;
- the lane outlives its peers — a peer that dies on a wall takes its churn
  tally with it (that is the bug), but the lane's wall tally does not go
  anywhere.

**Arming.** A failure is a *wall* when the account said no:

| class | signal | arms the lane |
| --- | --- | --- |
| quota | HTTP `429`, or the provider's own words — `rate limit`, `too many requests`, `quota exceeded` | **at once** |
| capacity | HTTP `529`, or the provider's own words — `overloaded`, `capacity`, `service unavailable`, `internal error` | on the **second** one in the window |

The classification is deliberately narrow, and it is read from the
**provider's** message, not from bro's wrapper: bro says
`acp <entry> unavailable — <reason>` about *every* failure it re-throws, so
the bare word "unavailable" is not a signal. Bro's own local caps
(`session quota reached`, `agents.<kind>.maxSessions`) are not the
account's wall either — they resolve on their own, and arming on them would
refuse a lane that is serving fine.

The threshold is what keeps the two guards apart. A quota wall is the
account saying no in so many words — it closes the lane at once. A generic
provider failure is a *failed turn*: one of them is an incident of that
turn, and only the second one in the window says the account is
struggling. Without the threshold the cooldown would answer every
provider hiccup, and the churn guard (`spec bro-b961a`) would never get to
see the churn it exists to stop. With it, the 2026-11-10 outage — 32
consecutive "Internal error" spawns — would have cost **two** sessions
instead of 32.

**The refusal.** While the cooldown holds, the lane answers a request with
`AcpCooldownError` — **before** the peer is linked and before
`session/new` is sent. The refusal therefore costs no session and no quota.
It reaches the client as:

| surface | answer |
| --- | --- |
| `/v1/messages`, `/v1/responses`, `/v1/chat/completions` | HTTP **429**, `retry-after: <seconds>`, `rate_limit_error` |
| `/api/v1/acp` (brokered transport) | JSON-RPC error `-32004` (the cooldown's own code) |

The `retry-after` is the cooldown's own remaining wait, so the client waits
exactly as long as the lane is closed — and MCode, which honours
`retry-after`, stops hammering instead of re-spawning.

**Escalation.** A lane that keeps hitting walls is a lane the account cannot
serve, and every probe costs a session. So the wait grows while the walls
keep coming: the first wall waits `acpCooldownMs`, the second twice that,
and so on up to a 15-minute ceiling. The provider's own `retry-after` is a
floor under the wait — the account knows better than bro when it recovers.
A quiet window (5 minutes) resets the tally, so a recovered account is
served immediately.

### Where the refusal is spoken

Two chokepoints, so the rule holds for every client of the lane — Claude
Code, Codex, Cursor, bro's own loop:

1. **the provider layer** — `acpSessionOpen` refuses before `session/new`.
   This is the guarantee: no client of this lane can spend a session while
   the wall holds;
2. **the conductor's `wire.link`** — the refusal lands before the peer is
   linked, so a refused request costs nothing at all. It covers all three
   wire dialects (`/v1/messages`, `/v1/responses`, `/v1/chat/completions`)
   from one place.

The brokered transport (`/api/v1/acp`) rides the same account, so it gets
the same cooldown, on its own transport-scoped lane.

## Contract

| surface | scope | on a wall | on the refusal |
| --- | --- | --- | --- |
| `/v1/messages`, `/v1/responses`, `/v1/chat/completions` | lane (entry) | the lane closes | HTTP **429** + `retry-after`, no session opened |
| `/api/v1/acp` | transport lane | the lane closes | JSON-RPC `-32004`, no session opened |
| every ACP session open (`acpSessionOpen`) | lane | — | `AcpCooldownError` before `session/new` |

### Config (`serve` section)

| key | type | default | meaning |
| --- | --- | --- | --- |
| `serve.acpCooldownMs` | int ≥ 0 | `60000` | how long a lane stays closed after the account refused; `0` disables the cooldown |

The env pin `BRO_PROVIDER_ACP_COOLDOWN_MS` overrides the file, next to
`BRO_PROVIDER_ACP_MAX_OPENS` and `BRO_PROVIDER_ACP_STALL_MS`.

## Tests

- a wall closes the lane and the **next request opens no session** — the
  session count is the proof (conductor, `/v1/messages` and
  `/v1/chat/completions`);
- the refusal carries a positive `retry-after`;
- a healthy lane is untouched — no wall, no refusal;
- a failure that is *not* the account saying no (an auth error) never closes
  the lane;
- **one** provider failure does not close the lane, and the **second** one
  does — the outage case of the incident;
- the cooldown can be switched off — the lane spawns through walls;
- provider level: the refusal is spoken **before** `session/new` — the fake
  agent records no session, on both the pooled and the retained path;
- the escalation doubles per wall up to the ceiling, the provider's own
  `retry-after` is a floor under the wait, and a quiet window resets the
  tally;
- a counted-but-unarmed wall does not close the lane and does not make the
  next wait longer;
- the classifier: a quota wall and a capacity wall are walls; bro's own
  wrapper word, bro's own session cap, a timeout and a bad model name are
  not; a refusal is never a wall (the wait never extends itself).

## Out of scope

- **The account's quota itself.** bro stops being a standing consumer of a
  wall; it cannot change what the operator's own session spends.
- **The dead-loop guard** (`spec bro-b961a`) stays as it is — the cooldown
  is the proactive half, the guard is the reactive one.
- **The lane's own rate gate** (`providers.<name>.rateGate`, bead
  `bro-56o2a`) — that knob answers for batch spawns and is a separate piece
  of work.
- **Cross-repo quota sharing** — the cooldown is per lane in this process.
  Two hosts on one account still add up; a shared quota plane is its own
  spec.
